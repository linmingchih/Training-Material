## 範例演示

想像這樣一個場景：工程師把一份 PCB 的 AEDB 檔案丟進工作資料夾，只丟下一句話——「幫我看一下這片板子的 VCORE 電源軌，壓降有沒有問題，順便看看溫度會不會過熱」，然後就去倒了杯咖啡。等他回來，桌上多了一份 `overview.html`：整片板子的電源網路已經依複雜度排好序，穩壓器、負載晶片、去耦電容的位置一目了然。點進 VCORE 那一列，另一份報告已經生成——DCIR 壓降分布圖、電流路徑上的電阻損耗、加上 Icepak 算出來的板卡溫度雲圖，全部套用同一套排版，附上一句判讀提醒：哪裡的壓降超出預期、哪個位置的溫度需要留意。整個過程中，AI Agent 自己決定了該先跑健檢、該選哪個模式分析、該用哪份 PyEDB／PyAEDT 語法建埠與求解、該去哪份參考資料確認一條容易忽略的規則——工程師沒有寫下任何一行程式碼，甚至不需要知道 DCIR、cutout、電熱耦合這些名詞背後的實作細節，只需要看懂最後那份報告、判斷結果合不合理。這正是這一整套 AI 模擬助理工作坊想要走到的終點：模擬工作不再是「工程師打開軟體、一步步操作」，而是「工程師描述需求、AI Agent 自己把整套流程走完、交出一份看得懂的結論」。

能撐起這個場景的，不是單一個聰明的模型，而是前面五章一路鋪陳下來的整套機制：第二章的 MCP 讓 AI 真的能連上 AEDT 動手操作；第三章的編程 Skill 讓它寫出來的 PyAEDT／PyEDB 程式碼靠得住；第四章的模擬助理 Skill 讓它知道「這個數字正不正常」而不只是「這行程式碼跑不跑得動」；第五章的工程基本功，則讓這一切能夠安全、可追溯地長期維護下去。這一章換個方式，不再談原則，而是直接拆解一個真正在用的 Skill，看看這些觀念實際落地之後長什麼樣子。要拆解的對象，是一支處理電源完整性（Power Integrity，簡稱 PI）分析的 `power-integrity-skill`——它涵蓋 PyEDB 疊構操作、HFSS 3D Layout 求解、AEDT Circuit 電路模擬，是一支同時橫跨編程細節與模擬判斷的複合型 Skill，剛好可以拿來對照前面每一章談過的觀念。

### 觸發描述：讓 AI 自己判斷用不用得上

打開這支 Skill 的 `SKILL.md`，最先看到的不是操作步驟，而是一大段寫在檔案最前面 YAML 區塊裡的 `description`。裡面密密麻麻列了各種情境：分析某個電源網路、產生 `overview.html`、跑 SYZ 阻抗掃頻、跑 DCIR 壓降分析、跑 DCIR+ET 電熱耦合、做模型萃取重建電路、做去耦電容最佳化⋯⋯每一種情境都寫得很具體，甚至連使用者「沒有明講 power integrity 或 PDN 這幾個字」的情況都考慮進去了。這正好呼應第三章談的「編程 Skill 與 MCP 的差異」：Skill 不需要被呼叫、不需要連線，AI 只要讀到這段描述、判斷任務相關，就會主動把整份知識載進來參考——這段 `description` 本身，就是漸進式披露的第一層、成本最低的那一層。

### 骨架與分層：SKILL.md、references/、scripts/、assets/ 的實戰版本

拆開資料夾，會發現它完全對得上第三章講的四塊分區，只是每一塊都填滿了真實內容：

- **`SKILL.md`**：不到兩百行，只講骨架——這支 Skill 能做哪幾種工作模式（SYZ、DCIR、DCIR+ET、CIRCUIT、OPT）、資料夾該怎麼命名（`jobs/{時間戳}_{網路名}_{模式}/`）、每個模式該按什麼順序跑哪幾支腳本、以及一份「絕不能做」的關鍵規則清單（例如絕不覆寫原始 AEDB、絕不在沒有 DCIR 的情況下單獨跑 Icepak）。細節一概不展開，只留一句「詳見某份參考檔案」。
- **`references/`**：厚重知識分門別類存放，`job_layout.md` 講資料夾規範、`rules_and_workflow.md` 是一份編號 R0 到 R29 的規則手冊、`api_reference.md` 收錄 PyEDB／HFSS 3D Layout 的 API 用法、`decap_matching.md`、`dcir.md`、`extract.md`、`opt.md` 則分別對應四種進階工作模式的細節。AI 平常不會去讀這些檔案，只有真正卡在某個模式的細節時，才點名去查對應的那一份。
- **`scripts/`**：三十幾支可以直接執行的 Python 腳本，從建立工作環境的 `ensure_venv.py`、板子健檢用的 `inspect_board.py`，到各模式各自的準備、求解、寫報告腳本一應俱全。這些腳本不是憑空生成的參考文字，而是真的可以被 AI 呼叫執行、跑出結果的程式——這就是第二章談的 MCP 與第三章談的編程 Skill，在同一支 Skill 裡合流的地方：Skill 提供「該用哪支腳本、參數怎麼填」的知識，實際執行時再交給環境去真的動手。
- **`assets/`**：放的是報告用的 HTML 樣板（`overview_template.html`、`syz_template.html`、`dcir_template.html` 等）、統一的報告樣式表，以及一個內建的 Murata 電容 S 參數庫（`assets/caps`）。有了這個庫，AI 幫使用者挑選替代電容時，不必自己猜測型號與規格，直接從現成的供應商資料裡比對。

### 模擬判斷力：不只是程式，還有「怎麼做才對」的經驗

如果只看 `scripts/`，這支 Skill 跟一般的編程 Skill沒有兩樣；真正讓它貼近第四章「模擬助理 Skill」精神的，是 `SKILL.md` 裡那份 R0 到 R29 的規則清單，裡面記錄的全是工程經驗，而不是 API 用法。舉幾個例子：

- **R26（先看總覽再挑網路）**：一定要先跑 `inspect_board.py` 產生 `overview.html`，把整片板子的電源網路依複雜度排序過一輪，再決定要分析哪一條軌——這是「先看全貌、再深入細節」的工程直覺，不是任何一支 PyEDB API 能告訴你的事。
- **R29（DCIR 與電熱分析互斥）**：明確規定「絕不能在沒有先解出 DCIR 的情況下，單獨跑 Icepak 電熱分析」——這是一條純粹來自實務踩過坑、才會被寫下來的地雷提醒，正是第三章說的「查到一次沒教過的操作，就該寫回 Skill」的具體成果。
- **讀 Z(f) 的判讀邏輯**：`SKILL.md` 裡甚至寫了一段「怎麼解讀阻抗曲線」的說明——SYZ 模式在直流附近量到高阻抗是正常的（因為電容看起來像斷路），不代表真的有問題；OPT 模式真正要盯的指標，是 1 kHz 到 100 MHz 之間的**峰值**阻抗，不是低頻的那個點。這種「數字看起來異常，但其實是正常現象」的判讀能力，正是第四章談的模擬助理 Skill 最核心的價值——它教的不是程式怎麼寫，而是**這個數字該怎麼解讀**。

### 工作流程：一個任務背後的完整路徑

實際使用時，一次分析大致會走過這樣的路徑：先跑健檢（`INSPECT`），確認板子上的電源網路、穩壓器、負載晶片與去耦電容分布；接著針對選定的電源網路，依需求選一種模式——只想看寬頻阻抗就選 `SYZ`，關心直流壓降就選 `DCIR`，還要看板子溫度分佈就加碼跑 `DCIR+ET`，需要重建可替換電容的電路模型就跑 `CIRCUIT`，想找出最佳去耦電容組合就跑 `OPT`；每種模式都遵循「準備（cutout、建埠）→ 求解 → 寫報告」的固定順序，最後統一輸出成同一套 CSS 樣式的 HTML 報告，並更新一份 `jobs.html` 索引頁，讓所有跑過的工作都能被追溯查閱。這一整套順序，正是第三章說的「範例本身就是一套從頭到尾的完整流程」——AI 從這支 Skill 裡學到的不只是某支 API 怎麼呼叫，而是「一個 PDN 分析案子該按什麼順序推進」。

### 工程基本功：這支 Skill 也遵守第五章的規矩

最後值得一提的是，這支 Skill 本身也老老實實遵守第五章談的那套工程紀律：它要求獨立的 `.venv`（而且明確指定不能用 AEDT 內建的 Python，因為那裡面沒有 `pyedb`）、所有輸出都放進帶時間戳的 `jobs/` 資料夾、絕不直接覆寫原始 AEDB、每一次分析都留下完整報告可供事後追溯。換句話說，這不只是一支示範「Skill 該怎麼寫」的教材，它同時也是一份「一支夠格上線使用的 Skill，該具備哪些紀律」的活教材——把前面五章談的每一個觀念，都摺進了同一份檔案裡。
