## 模擬助理 Skill

上一章的編程 Skill，教會 AI 怎麼把 PyAEDT 的程式碼寫對；但「寫對程式」跟「做對模擬」是兩回事。資深工程師真正值錢的，往往不是「怎麼呼叫這個 API」，而是「為什麼要這樣設定」「這個結構要特別注意什麼」「這份規格書裡藏著哪些眉角」。這一章要處理的，正是這一層更深、更難複製的知識——模擬助理 Skill，也是整堂課「傳承」這個核心命題真正要落地的地方。

### 為何需要模擬助理 Skill

編程 Skill 教的是「通用的工具知識」——不管換到哪個專案、哪個客戶，PyAEDT 的 API 用法都一樣。但模擬助理 Skill 要裝的，是「特定情境下的判斷力」：這個連接器要怎麼簡化建模才不會犧牲精度、這種疊層結構的網格收斂準則要多嚴、這個客戶的產品線有哪些命名與公差慣例、上一個類似案子踩過哪些坑、後來怎麼解決的。這些東西，你翻遍 PyAEDT 官方文件也找不到——它們只存在資深工程師的腦袋裡，或是散落在內部信件與會議紀錄中，從來沒有被有系統地寫下來過。

模擬助理 Skill 要做的，就是把這些「屬於你們公司、屬於這個專案」的隱性知識，寫成一份活的 `SKILL.md`（以及配套的案例、檢查清單），讓任何一個接上這份 Skill 的 AI Agent，在處理這個特定領域的任務時，表現得像是已經帶了十年經驗的老工程師，而不是一個什麼都得從頭猜的新人。

### 引導 AI Agent 進行模擬任務

這份知識不太可能靠「坐下來一次寫完」生成，更務實也更貼近現實的做法，是真的把 AI 當成一個新人來帶：交付一個實際任務，讓它透過上一章打造的環境（Skill + MCP）動手嘗試，然後在每個關鍵節點停下來檢視它的選擇——這裡的邊界條件設對了嗎、這個網格密度合理嗎、這個簡化假設站得住腳嗎。當它做錯或做得不夠好時，不只是糾正結果，更重要的是明確講出「為什麼」——正是這個「為什麼」，才是真正該被記錄下來、值得傳承的部分。

經過幾次、幾個不同專案的實際帶練之後，會慢慢浮現出兩種資訊：一種是「這個規則放諸四海皆準，該變成永久規則」，另一種是「這只是這個案子的特例，不該一概而論」。這個階段務必保留人在迴路中（Human-in-the-loop）的把關，因為此刻任何沒被抓到的錯誤判斷，都有可能在下一步被寫進 Skill、之後被反覆套用、錯得更systematic。

#### PI 範例：養成一支 PI-Z-Skill

用一個實際的 PI（電源完整性）案子，感受一下這個帶練過程長什麼樣子。

第一步，先讓 AI 熟悉這片板子：「請用 PyEDB 讀取這片主機板的 Layout，列出 CPU 所有電源網路，以及每個網路上對應的 Decap（去耦合電容）數量。」AI 執行後回報一張清單。接著追加：「請畫出其中 Vdd 這個電源網路的 Decap 分布圖。」AI 照做，畫出電容在板子上的位置分布——這一步是在確認它「看得懂」板子與網路的對應關係。

第二步，進入實際建模：「在這顆 Choke 電感的位置設一個對 Reference 的 Port，阻值設 0.01 歐姆；在 CPU 的位置設一個 Pin Group Port。」跑完之後匯出結果，檢查 Z11 曲線合不合理——這是資深工程師的直覺判斷，也是最該被記錄下來的一步：Z11 在哪個頻段該是電感特性、哪個頻段該平坦、數量級大概落在哪裡，這些「合理性判斷準則」正是模擬助理 Skill 要裝進去的核心內容。

第三步，確認 Z11 合理之後，往下推進：「根據每顆電容的容值與封裝尺寸，到我們的常用電容模型目錄裡，找出對應容值的實際廠商模型，把理想電容換掉。」這一步務必人工檢查 AI 到底換得對不對——容值有沒有找對、封裝尺寸有沒有對應到正確的模型，不能因為它「看起來換了」就直接放行。確認無誤後，再補上模擬設定（例如頻率範圍、掃描點數）並執行模擬、輸出結果，最後再檢查一次輸出是否合理。

整個任務走完之後，才是這一章真正的重點：請 AI Agent 回顧整段對話，把用到的正確流程步驟、關鍵判斷準則（例如 Z11 該長什麼樣子才算合理、電容模型該怎麼挑）、以及呼叫過的 API，整理寫進一支專屬的 `PI-Z-Skill` 裡。之後如果要延伸應用——例如把這組 S 參數模型丟進 Circuit 裡做 Decap 選型優化——AI Agent 可以直接調用 `PI-Z-Skill` 裡已經記錄好的知識，不必每次都從頭摸索一遍。隨著這支 Skill 一次次被實際任務呼叫、修正、擴充，AI Agent 對這類 PI 分析就會越來越熟練，逐漸表現得像是真的做過上百個案子的資深工程師。

### 讓 AI Agent 將學到的經驗寫回助理 Skill

當一次任務或一個階段性檢查點結束後，可以明確請 AI 做一件事：回顧這次任務中有哪些是「可以重複使用的心得」，並提議把它寫回 Skill 檔案——可能是新增一條規則、補上一個範例案例、或修正一個先前寫錯的假設。這個「寫回」的動作，其實跟這套工作環境本身用來跨對話保留知識的記憶機制是同一個概念：把當下學到的東西，依照適用範圍分層留存下來，讓下一次任務、甚至下一位使用者，都能接續使用。

這裡有一個不能省略的原則：AI 提出的更新，一定要以「差異（Diff）」的形式呈現，交給人審核、確認後才正式合併，絕對不要讓它未經檢視就直接覆寫 Skill 檔案。原因很直接——如果把一次性的特例，誤寫成長久適用的規則，這個錯誤會被之後每一次任務都重複套用，而且不容易被發現，是這類系統最典型也最隱蔽的失敗模式。以前面 `PI-Z-Skill` 的例子來說，就是先看過 AI 整理出來的 Z11 合理性準則與電容挑選邏輯是否真的正確，確認沒問題才合併，而不是照單全收。

### 持續訓練優化 Skill

把模擬助理 Skill 當成一份「活的文件」來經營，並且跟第五章要談的版本控制綁在一起：每一次合併更新，都對應一次 Git commit，用跟審查程式碼一樣的標準去看每一次的差異；指定一位「負責人」（通常就是資深工程師本人）定期檢視、清理過時或錯誤的規則；當多位工程師各自帶出不同的學習成果時，也是由這位負責人去整合、去解決衝突。當一份 Skill 涵蓋的情境越來越龐雜時，同樣適用第三章提過的原則——與其硬撐成一份巨型檔案，不如適時拆成幾份更聚焦的子 Skill。

長期累積下來，這份 Skill 會變成一份持續增值、可查詢、不會因為某位資深工程師離職而消失的機構記憶（Institutional Memory）。像 `PI-Z-Skill` 這樣的例子，會隨著一次次被拿去做不同的 Decap 優化案子而持續茁壯，每多跑一個案子，就多驗證、多累積一點判斷準則，AI Agent 也就越用越上手。這正是這整堂課最終想達成的目標：把原本困在少數人腦袋裡的模擬經驗，變成一份可以被交接、被檢視、被持續進化的數位資產。
