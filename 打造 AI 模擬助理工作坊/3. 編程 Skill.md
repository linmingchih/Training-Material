## 編程 Skill

有了 MCP，AI Agent 終於能「動手」操作 AEDT 了。但動手不代表動得對——如果 AI 對 PyAEDT 的 API 用法一知半解，遇到 MCP Server 沒有事先包好的操作，它一樣得自己寫程式，也一樣可能生出「看起來合理、實際上會噴錯誤」的程式碼。這一章要介紹的「編程 Skill」，就是用來補上這塊拼圖：讓 AI 在動手之前，先讀懂一套「內部教材」，把程式寫得又快又準。

### 為何需要編程 Skill

MCP 給的是「即時連線」的執行能力，但它不可能把每一種可能的操作都事先包成 Tool——模擬工作的變化太多了，總會遇到 MCP Server 沒有預先設計好的客製任務，這時候 AI 還是得自己動筆寫 PyAEDT 程式碼。問題是，PyAEDT 的類別、方法名稱、參數順序、版本間的差異，對 AI 來說跟任何一套陌生的 API 沒兩樣，它很容易「憑印象」生出一個聽起來很合理、但實際上不存在的方法呼叫，或是用錯參數導致邊界條件設反、單位算錯。

更根本的問題是：MCP 的每一個 Tool，對應的是「單一動作」——建端口是一個 Tool、設邊界條件是另一個 Tool、跑分析又是另一個 Tool，它們彼此是獨立的，MCP 本身並不知道「一個完整的模擬案子，這些動作該按什麼順序組合起來」。換句話說，MCP 知道「怎麼做每一步」，卻不知道「整個流程該怎麼走」。這正是編程 Skill 要補上的另一塊拼圖。

「Skill」（例如 Anthropic 的 Agent Skills，以一個 `SKILL.md` 檔案加上一組參考資料組成）解決的正是這個問題：它是一包可以被 AI 隨需載入的靜態知識——正確的類別用法、常見任務的範本程式、已知的地雷與繞過方式。這就像是新人到職第一天，與其讓他自己上網亂查、亂試錯，不如直接給他一本「內部工程手冊」，裡面寫的是「我們公司都是這樣寫」的具體做法。

### 編程 Skill 與 MCP 的差異

這兩者很容易被搞混，但角色完全不同，值得說清楚。MCP 是一條「即時的橋樑」——它是一支正在執行、隨時待命的伺服器程式，扮演的是 AI 的「手與神經系統」：AI 呼叫、伺服器執行、真實世界（AEDT）產生變化、結果回傳。Skill 則是一份「靜態的知識包」——就是資料夾裡的幾個檔案，扮演的是 AI 的「教科書與肌肉記憶」：不需要啟動任何伺服器，AI 在準備回答或動手之前，會依照描述判斷這個任務是否用得上這份 Skill，用得上就把內容讀進來參考。

兩者也可以獨立存在：只有 Skill、沒有 MCP，AI 能寫出正確的腳本，但得靠人手動去執行、看結果；只有 MCP、沒有 Skill，AI 能執行預先包好的操作，但一旦遇到需要自己寫程式碼的場合，品質就沒有保障。真正好用的模擬助理，是兩者疊加：Skill 負責「教它寫對」，MCP 負責「讓它真的能跑、能看到結果」，兩邊形成一個完整的迴路。

這裡有一個更精確的分工邏輯，值得特別拉出來講：編程 Skill 是從既有的範例訓練出來的，而這些範例本身，通常就是一套從頭到尾的完整流程——建模、設定邊界與激勵、執行模擬、最後抓取並整理結果資料。因此 AI 從 Skill 裡學到的，不只是「某個 API 怎麼呼叫」，而是「一個模擬案子該按什麼順序推進」。但範例終究是有限的，難免會遇到範例裡沒教過的特殊操作。這時候正確的做法順序是：AI Agent 先查 Coding Skill，掌握整體流程該走到哪一步、下一步該做什麼；如果發現這一步是範例沒涵蓋到的操作，才轉而透過 MCP 去查詢當下有哪些可用的 Tool、對應的參數格式是什麼，藉此補上這個流程裡的缺口。Skill 負責「路線圖」，MCP 負責「路上臨時查地圖」，兩者搭配，才能既走對順序、又不會被範例沒教過的特例卡住。

不過，透過 MCP 現查現用，成本比想像中高——每一次工具探索（列出有哪些 Tool、讀取參數規格）與呼叫，都要佔用不少 Token，而且是每次任務都要重新查一遍，長期下來的累積開銷相當可觀。因此有一個很實際的優化原則：**只要透過 MCP 查到一次沒教過的操作該怎麼寫，就該順手把這段用法補寫進 Coding Skill 裡**，變成一筆新的參考範例。下一次再遇到同樣的操作，AI 就能直接從 Skill 裡便宜、快速地讀到答案，不必再繞去問 MCP。換句話說，MCP 查詢應該被當成「補齊 Skill 缺口」的手段，而不是每次都要依賴的常態管道——Skill 的涵蓋範圍會隨著一次次的現場查詢，自然而然越補越廣，長期下來對 MCP 的依賴度會逐漸降低，整體回應也會越來越快、越省成本。這個「查到就寫回去」的習慣，跟第四章要談的模擬助理 Skill 持續進化的做法是同一套精神，只是這裡補的是程式寫法，第四章補的是模擬判斷。

### 訓練自己的編程 Skill

理解了角色分工，接下來就是實作面：如何真的動手訓練一套屬於自己的 PyAEDT 編程 Skill？大致分成三個階段：先收集素材、再借助工具整理成標準格式、最後反覆測試修正。

#### 爬蟲下載

第一步是把散落各處的知識收集起來，變成可以餵給 Skill 的素材庫。常見來源包括：PyAEDT 官方文件站（API Reference、Examples Gallery）、GitHub 上的原始碼與範例腳本、以及版本更新紀錄（Changelog，這點特別重要，因為 PyAEDT 的 API 會隨版本演進，同一段程式碼可能在新版失效）。可以寫一支簡單的爬蟲或下載腳本，把這些頁面整批存成本地的 Markdown 或純文字檔，作為後續整理 Skill 的原始資料，同時務必記錄清楚這批素材對應的 PyAEDT 版本，避免日後版本錯亂。

#### Anthropic Skill Creator

有了原始素材，不必從零設計 Skill 檔案該長什麼樣子——Anthropic 提供了一支「Skill Creator」meta-skill，本質上是一個「用來製作 Skill 的 Skill」。它會引導你釐清這個 Skill 的邊界與用途，把雜亂的原始素材整理成結構完整的 `SKILL.md`（包含給 AI 判斷何時該觸發使用的 description、以及分門別類存放的參考資料與範例腳本），並套用官方建議的最佳實踐，例如「描述要精準」「厚重的參考內容要獨立成檔案、不要塞爆主檔案」。事實上，各位現在使用的這套工作環境裡，本來就已經內建了一批針對 HFSS、Q3D、Icepak、Maxwell 等產品的 PyANSYS Skill——它們就是用同樣的方法論打造出來的，是最好的現成案例。

#### 創建自己的 編程 Skill

實際動手時，建議依循這樣的流程：第一，先定義這個 Skill 的邊界與命名——原則是「一個工具、一支 Skill」，例如 HFSS 3D 一支、Q3D 一支，避免把所有東西塞進一支龐大到 AI 也搞不清楚何時該用的巨型 Skill；第二，撰寫精準的觸發描述，讓 AI 一看就知道什麼情境該叫用它；第三，把常見任務整理成一支支小範例腳本放進參考資料夾，而不是全部寫進主檔案裡，避免佔用過多的上下文空間；第四，反覆用真實任務去測試——實際問 AI 一個模擬問題，觀察它是否真的載入了這份 Skill、產生的程式碼是否正確，發現遺漏就補上案例、發現描述模糊就修得更精準；第五，像管理程式碼一樣，用 Git 為每次更新留下版本紀錄，讓 Skill 也能像正式的程式專案一樣被追溯、被回退。
