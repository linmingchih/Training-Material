## 概要

在動手介紹任何工具之前，我們得先想清楚一件事：這堂課到底想解決什麼問題？

過去，模擬工程師的養成幾乎都是「師徒制」——老手帶新手跑案例、除錯、調網格、判斷結果合不合理，這些眉角很少寫成正式文件，大多留在資深工程師的腦袋和肌肉記憶裡。當這些人退休、離職、或轉調到別的專案，公司帶不走的，往往就是這些最值錢的經驗。

這門課的核心命題很簡單：**能不能用 AI Agent，把這些說不清楚、寫不出來的隱性知識，轉換成可以複製、可以查詢、甚至可以持續進化的數位資產？** 我們會用 PyANSYS 作為統稱、以 PyAEDT 作為主要示範對象，帶各位看一遍「從零打造一個懂你們家模擬眉角的 AI 助理」的完整路徑。由於時數有限（約 5 小時）且以講師示範為主，請把這堂課當成一趟「參觀 AI 助理誕生現場」的觀摩行程，回去之後再依樣畫葫蘆動手做。

整堂課的骨架是這樣的：先看懂 AI Agent 現在能做到什麼、不能做到什麼（本章）；再學會怎麼讓 AI 真的「動手」操作 ANSYS 工具（第二章 MCP）；接著教它把程式寫得又快又對（第三章 編程 Skill）；再進一步把資深工程師的判斷力灌輸進去（第四章 模擬助理 Skill）；最後補上一套要長期維護這個助理所需要的基本功（第五章 建議必備技能）。五章環環相扣，缺一不可。

### AI Agent 現狀

這幾年 AI Agent 的進展，用「一日千里」形容並不誇張。從最早只能聊天回答問題的 Chatbot，到現在可以自己開終端機、寫程式、跑測試、讀錯誤訊息再自己修正的「Coding Agent」（例如 GitHub Copilot、Claude Code 這一類工具），AI 已經從「回答問題的助手」進化成「會動手做事的同事」。這個轉變背後的關鍵技術，是讓大型語言模型（LLM）具備「工具呼叫（Tool Calling）」能力——它不再只是吐文字，而是可以決定「我現在要呼叫哪個工具、帶什麼參數」，再根據工具回傳的結果決定下一步動作。這正是 Agent（代理人）之所以叫做 Agent 的原因：它會自主規劃並執行一連串步驟，而不是被動地一問一答。

放到工程模擬的場景來看，這代表 AI 已經有能力：讀懂一份規格文件、生成對應的模擬腳本、透過程式介面驅動模擬軟體執行、讀取結果檔案、判斷是否收斂或合理，並在不合理時自己嘗試修正參數重跑。這一整條鏈路，理論上都可以交給 Agent 自動完成。

但現況也不是萬能。目前 AI Agent 仍有幾個明顯的天花板：第一，它對「通用程式碼」很熟，但對「你們公司特有的模擬慣例」完全陌生——它不知道你們的網格加密規則、不知道哪個結構要特別注意收斂、不知道你們命名變數的習慣。第二，它容易「一本正經地講錯話」（Hallucination），尤其是在 API 用法上，可能生出一個聽起來很合理、但實際上不存在的函式呼叫。第三，它的「記憶」有限——每次對話結束，除非刻意把知識留存下來，否則它學到的東西會歸零。這三個限制，正好對應接下來三章要解決的問題：MCP 解決「怎麼連上工具」、編程 Skill 解決「怎麼寫對程式」、模擬助理 Skill 解決「怎麼記住你們的眉角」。

### 利用 AI Agent 來完成模擬任務

具體來說，一個模擬工程師可以怎麼「使喚」AI Agent？最直覺的方式，就是把原本要交代給新人的話，直接打字（或用講的）交代給 AI。差別在於，AI 背後接上了 PyANSYS 這一整組 Python API，所以它不是紙上談兵，而是真的可以生成腳本、呼叫 AEDT、跑出結果。

下面用三個模擬工程師最常見的任務類型——訊號完整性（SI）、電源完整性（PI）、射頻（RF）——各舉一個 Prompt 範例，感受一下「交代任務」與「傳統寫 Script」的差別：交代任務時，你講的是「目的」與「限制條件」，而不是逐行的程式邏輯；程式邏輯的部分，交給 AI 去查閱它學過的 PyAEDT 知識自己生成。

#### SI Prompt範例

> 「請用 PyAEDT 開啟目前這片主機板的 HFSS 3D Layout 設計，針對 DDR5 的 Data 與 Strobe 訊號線建立差動端口，設定 10MHz 到 20GHz 的離散頻率掃描，跑完之後幫我畫出插入損耗（Insertion Loss）與回波損耗（Return Loss）的曲線，並標出 -3dB 頻寬。」

這類 SI 任務的重點在於「端口設置是否正確」與「掃描頻段是否符合訊號速率」，AI 需要理解差動對的命名規則、知道 DDR5 的目標頻寬大概落在哪裡，這些正是後面模擬助理 Skill 要灌輸的知識。

#### PI Prompt範例

> 「幫我在這顆 IC 的電源網路（Power Net）上，於晶片 Pin 位置與電容擺放位置之間建立阻抗掃描，輸出從 DC 到 100MHz 的 PDN 阻抗曲線，並標示出目標阻抗（Target Impedance）的紅線，看看哪些頻段超標。」

PI 任務的挑戰在於網路（Net）數量龐大、去耦合電容（Decap）擺放組合眾多，AI 若具備正確的 PyAEDT 操作知識，可以快速掃過大量參數組合，把原本要花一整天的苦工，壓縮到幾分鐘生成初稿。

#### RF Prompt範例

> 「請幫我在 HFSS 中建立一組微帶線（Microstrip）巴倫（Balun）結構，掃描 2.4GHz Wi-Fi 頻段的 S 參數，並確認差動轉單端的相位差是否落在 180±5 度以內。」

RF 任務通常牽涉到更細膩的幾何與邊界條件設定，這也是為什麼「光有 MCP 連上工具」還不夠——沒有正確的領域知識做後盾，AI 生出來的模型可能幾何正確、但物理意義是錯的。

### 訂做AI Agent 考量

看完範例，很多人第一個念頭是：「那我直接訂閱一個現成的 AI 工具不就好了？」理論上可行，但要打造一個真正好用、划算、又安全的模擬助理，還有幾個現實面的取捨要考慮。

#### AI Agent 模型選用

不同的 LLM 模型，在「程式碼生成品質」「工具呼叫穩定度」「推理能力」「反應速度」上表現差異很大。目前主流大致可分三個梯隊：第一梯隊是像 Claude Opus、GPT-5 這種旗艦模型，推理能力最強、最不容易寫錯程式，但成本也最高、速度較慢；第二梯隊是像 Claude Sonnet 這類中階模型，是目前多數 Coding Agent 的預設選擇，兼顧品質與成本；第三梯隊是輕量化模型，適合處理簡單、重複性高、容錯率較高的任務（例如批次重新命名、格式轉換）。選型的關鍵在於：先想清楚模擬助理平常要處理的任務複雜度，再對應到合適的模型梯隊，而不是無腦選最貴的。

#### 能力與成本成正比

這句話幾乎是這個領域的鐵律：模型能力越強，每次呼叫（Token）的價格越高，回應也越慢。實務上常見的策略是「分工」——用強模型做規劃與決策（例如判斷這次模擬要用什麼邊界條件、怎麼拆解任務），用弱模型（甚至規則式腳本）做重複性高的執行細節（例如批次匯出圖檔、整理報告格式）。這種混合架構可以把整體成本壓在合理範圍，同時保留關鍵決策的品質。另外要提醒的是：模擬工作往往一個任務要跑很多輪（改參數、重跑、再改），如果每一輪都用最貴的模型從頭跑一次，成本會非常可觀，這也是為什麼後面會強調「把知識固化成 Skill」的重要性——固化後的知識可以讓便宜的模型也表現得像資深工程師。

#### 訓練與微調

除了「選現成模型」之外，另一條路是「微調（Fine-tuning）」——用公司內部累積的模擬案例、報告、往來紀錄，去調整模型的參數權重，讓它更貼近公司的語言與慣例。但微調的門檻遠高於一般想像：需要足量且乾淨的訓練資料、需要 GPU 運算資源、還要面對資料外流與智財權的風險考量。因此，這堂課會把重點放在成本更低、更快回收效益的做法——透過 Skill（技能包）與 MCP（工具連接）的組合，在「不動模型本身」的前提下注入領域知識。微調更適合當作長期、資料量累積到一定規模之後的加值選項，而不是入門的第一步。

### Synopsys 相關Roadmap

以下方向為產業趨勢的一般性觀察，實際產品規劃與時程請以 Synopsys 官方公告及業務窗口提供的最新資訊為準。整體而言，可以觀察到幾個明確的方向：其一，Synopsys 持續投入「AI 驅動的設計與驗證」，讓 AI 輔助逐步滲透到從晶片設計到系統模擬的各個環節；其二，PyANSYS 系列（PyAEDT、PyEDB、PyMechanical 等）持續朝開源化、模組化發展，這讓 MCP、Skill 這類「外部 AI 工具接軌」的模式有了更穩固的地基；其三，業界對 MCP 這類開放協定的採用度快速上升，可以預期未來會有更多官方或半官方的 MCP Server 出現，降低企業自建串接的門檻。對各位而言，現在投入學習「如何用 Skill 與 MCP 訓練專屬模擬助理」，本質上是在為即將到來的官方工具生態，提早練好基本功。
