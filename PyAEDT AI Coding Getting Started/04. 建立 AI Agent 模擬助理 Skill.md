04. 建立 AI Agent 模擬助理 Skill
---
### 為什麼需要 Skill

上一章讓 AI 能連上 AEDT、真的動手執行任務，但 AI 對「你們家特有的模擬慣例」仍然陌生——它不知道你們網格加密的規則、不知道哪種結構要特別注意收斂、也不知道你們命名變數的習慣。**Skill** 就是把這些重複出現、但從來沒正式寫成文件的操作慣例與判斷標準，轉換成一份 AI 能直接讀懂、並重複使用的指令模板。寫一次 Skill，之後每次交代同類任務時，AI 都會自動參考這份模板，不必每次重新推理一次。

### Skill 概念的演進

「Skill」這個做法不是憑空出現的，而是一路從「每次對話都重新描述規則」演化來的：最早大家靠純 Prompt Engineering，每次都得在對話裡重新交代一次規則、慣例；接著出現 RAG（檢索增強生成），把知識庫外部化、讓 AI 自己檢索文件來回答，但仍然缺少「這種情境該用什麼步驟執行」的可執行性；2023 年左右出現的 Custom GPTs、Plugins 進一步把特定領域知識與工具包裝成可重複呼叫的單元，但仍偏對話層級。到了 2025 年，Anthropic 正式推出 Claude Skills，定義了 `SKILL.md` 的規格與「Progressive Disclosure（逐步揭露）」機制：讓 Agent 依需載入知識，而不是一次把所有文件塞進 context window，讓知識可以模組化、可攜帶、可分享。目前 GitHub Copilot、VS Code 等主流 Coding Agent 工具都採用了類似的 Skill 格式。這門課使用的 Skill 概念，延續的就是這條脈絡：目的是把資深工程師的隱性知識，轉換成 AI 能依需載入、可重複使用的檔案。

### SKILL.md 檔案結構

一個最小可用的 Skill，通常就是一個資料夾裡面放一份 `SKILL.md`，開頭用 YAML frontmatter 宣告它的名稱與觸發時機：

```markdown
---
name: hfss-differential-port
description: 當使用者要在 HFSS 3D Layout 建立差動端口時使用。
---

## 步驟
1. 確認差動對網路命名規則（例如 `_P` / `_N` 結尾）
2. 呼叫 `create_wave_port`...

## 範例程式碼
```

`description` 是 AI 決定要不要自動載入這份 Skill 的關鍵，描述得越精確，觸發時機就越準。內文則是真正的知識本體：步驟拆解、判斷標準、常見陷阱、以及可直接套用的程式碼範例。

### Skill 的目錄結構

當 Skill 的內容越來越複雜，光靠一份 `SKILL.md` 往往不夠用，這時候會搭配幾個標準子目錄，讓知識依「使用時機」分層載入，避免一次塑爆 context window：

```
hfss-differential-port/
├── SKILL.md          # 入口檔，frontmatter + 核心步驟
├── references/       # 進一步參考資料，需要時才展開讀取
├── scripts/          # 可直接執行的輔助腳本或工具
└── assets/           # 樣板、範例檔案、圖片等靜態資源
```

- **SKILL.md**：入口檔案，只有 frontmatter（name/description）與核心步驟會被優先載入，AI 決定要不要觸發這個 Skill，全靠這裡的 `description` 寫得準不準。
- **references/**：放進一步的參考資料（例如完整 API 規格、公司內部規範文件），只有當 AI 判斷需要更深入的細節時才會展開讀取，平常不會佔用 context。
- **scripts/**：放可以直接執行的輔助腳本或工具（例如驗證腳本、格式轉換工具），AI 可以直接呼叫執行，而不需要每次重新生成同樣的程式碼。
- **assets/**：放樣板、範例檔案、圖片等靜態資源（例如標準報告樣板、標準疊層 Excel 範本），Skill 執行時可以直接複製套用，不需要每次重新產生。

簡單的 Skill 不一定需要全部三個子目錄都存在，但當需要附帶大量參考文件、可執行工具、或固定樣板時，把它們分開放到對應目錄，比全部堵在 `SKILL.md` 裡更容易維護、也更節省 context。

### 撰寫技巧

- **情境觸發要精準**：`description` 要寫出「什麼情況下該用這個 Skill」，而不只是重述它做什麼。
- **步驟拆解要可執行**：避免模糊的描述（例如「設定好邏輯」），改寫成具體呼叫哪個 API、帶什麼參數。
- **內嵌範例程式碼作為模板**：讓 AI 直接參考既有可執行的片段，而不是重新發明寫法。
- **紀錄常見陷阱**：把之前進行中踩過的坑（例如某個參數單位是 mil 不是 mm）寫進去，避免下次重踩。

### 從對話萃取 Skill：讓 AI 幫你寫 Skill

比起憑空想像該寫什麼進 Skill，更實用的做法是：先在對話中，把資深工程師的判斷一步步「教」給 AI，走完一次完整的模擬任務，再請 AI 把這次對話整理成一份 Skill。實際流程大致如下：

1. **在對話中一步步引導 AI 完成一整個模擬工作**：例如針對某片實際板子，逐步交代「先切這個區域」「這個網路要建差動埠」「用這個頻段掃描」「這個結果不合理，因為參考平面沒接地，改成這樣」，過程中你不斷確認、修正 AI 的判斷，直到整個訊號完整性（SI）分析或天線設計流程真的跑出合理結果。
2. **請 AI 依照 Skill-Creator 規範，把這次對話萃取成 Skill**：直接告訴 AI「把我們剛剛做的這件事整理成一個 Skill」。這一步 AI 會從對話歷史中萃取意圖（做了什麼、用了哪些工具、你做過哪些修正、輸入輸出格式長什麼樣），先跟你確認範圍，再依照標準格式寫出 `SKILL.md`（精準的 `description`、可執行的步驟、常見陷阱），並視需要把可重複使用的程式碼放進 `scripts/`、把詳細規格放進 `references/`。
3. **依專業領域拆成多份 Skill**：不用把所有知識塞進一份萬用 Skill，比較好的做法是依任務類型拆分，例如 `signal-integrity-skill`（差動對建模、S 參數判讀、眼圖分析慣例）、`antenna-design-skill`（天線幾何參數化、遠場方向圖判讀、頻寬調校慣例）、`power-integrity-skill`（PDN 阻抗掃描、去耦合電容選型慣例）等，每份各自聚焦一個領域，`description` 才容易寫得精準、也才不會互相干擾觸發時機。
4. **用新任務驗證、再修正**：拿一個類似但不完全相同的任務去測試這份新 Skill，看 AI 是否真的套用了正確的步驟；若發現遺漏或誤判，回頭補進 Skill 內文，而不是每次都重新在對話裡口頭糾正。
5. **訓練完成後，納入 Git 版本保存**：確認這份 Skill 可用後，立刻 `git commit`，之後每次修訂（補陷阱、調整 `description`、拆分新領域）都各自留下紀錄，而不是直接覆蓋舊檔。這樣做的好處，在下一章談自動化程式的版本控制時會更清楚：Skill 本質上也是一份會持續演進的知識資產，沒有版本紀錄，遇到「改壞了但忘記原本怎麼寫」時就無從救起。

這個「先示範、再萃取、再拆分、再驗證、再保存」的流程，能把單次對話中花掉的推理成本，轉換成日後每次都能重複使用的資產，也是把資深工程師隱性知識系統化保存下來最實際的做法。

### Skill 的持續優化

Skill 寫完不代表結束，它永遠有改進的空間，應該當成一份會持續演進的文件來維護，而不是寫一次就束之高閣：

- **每次用完就覆盤**：每次套用某份 Skill 完成一次實際任務後，讓 AI Agent 順手做一次覆盤——這次執行中有沒有遇到 Skill 沒寫到的新判斷或新陷阱？有沒有哪個步驟其實走不通、需要修正？把新學到的東西寫回 Skill，也把已經過時、不再適用的舊資料（例如已棄用的 API、不再使用的命名規則）從 Skill 裡移除，避免 Skill 隨時間累積越來越多矛盾或過時的內容。
- **隨時用 Skill-Creator 優化**：不需要等到 Skill 出問題才動手，可以隨時請 AI 依照 Skill-Creator 的做法重新檢視既有 Skill——例如優化 `description` 的觸發準確度、精簡冗長或重複的步驟、把常被問到的邊界情況補進常見陷阱，讓 Skill 保持精簡且好用。
- **訓練用強模型、日常用一般模型省成本**：撰寫或萃取 Skill 這個階段，建議用推理能力較強的旗艦模型，確保萃取出來的判斷標準與步驟正確、經得起檢驗；但 Skill 一旦固化成文字後，日常套用這份 Skill 執行任務時，可以改用一般、成本較低的模型，因為模型不需要再現場推理一次規則，只要照著 Skill 內文執行即可，這樣既維持了品質、也大幅降低長期使用的 Token 成本。
